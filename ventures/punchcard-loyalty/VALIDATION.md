# Validation Report — PunchCard Loyalty

**Overall status: PASS-WITH-FIXES**

Audited independently against the claimed spec and the audit checklist. Two files present as expected (`index.html`, `README.md`). Both inline script blocks (main app + the script template embedded inside the generated `card.html`) were extracted and syntax-checked with `node --check` and `new Function()` — all clean, before and after fixes. The exported card's `buildStandaloneCardHtml()` function was executed directly in Node (not just read) against multiple business names, including an apostrophe/ampersand name (`Joe's Coffee & Tea`), an XSS-attempt name (`<script>alert(1)</script>`), an empty name, and a symbols-only name, to verify the generated HTML and embedded JS.

## Issues found and fixed

1. **Crash risk in the exported card on malformed localStorage state (real defect, fixed).** The exported card's own `render()` function read `state.stamps.length` with no guard, unlike the main app's equivalent renderer which safely does `state.stamps ? state.stamps.length : 0`. If `localStorage` for a card's key ever held a valid JSON object that simply lacked a `stamps` array (plausible from partial writes, manual tampering, or a future format change), `loadState()` returned that object as truthy, skipped default-initialization, and `render()` would throw `TypeError: Cannot read properties of undefined (reading 'length')` — a hard crash on the customer's actual punch card. Reproduced this crash against the pre-fix code with a Node/DOM shim, then fixed and re-verified no crash post-fix.
   - Fix: `var count = (state.stamps && state.stamps.length) || 0;` (was `state.stamps.length`).
   - Fix: guarded the stamp-add handler with `state.stamps = state.stamps || [];` before `.push()`.
   - Fix: hardened `loadState()` in the exported card to require `Array.isArray(p.stamps)` (and reject top-level arrays) before accepting saved state as valid, so any malformed shape now safely re-initializes instead of limping into a later crash.
   - Applied the equivalent array/object-shape hardening to the main app's `loadSetup()` and `loadDemo()` for consistency (they were not currently reachable from a crash, since the main app's renderer already guarded stamp access defensively, but the stricter guard closes the same class of bug before it could bite a future edit).

No other functional defects were found. Specifically verified and confirmed correct (no changes needed):

- **PIN comparison is pure string equality throughout** (`entered === CFG.pin`, `entered === activeCorrectPin`) with no `parseInt`/`Number()` anywhere near PIN handling. A PIN of `"0123"` round-trips correctly: the setup input strips non-digits and keeps leading zeros as a string, the exported card's `CFG.pin` is JSON-string-serialized (preserves `"0123"` verbatim), and digit-box comparison is string-joined. Confirmed via direct execution.
- **HTML/JS escaping of business names**, including apostrophes and HTML-special characters. `esc()` correctly escapes `&<>"'` for the `<title>`/meta HTML context. The embedded `CFG` object is built via `JSON.stringify(...).replace(/</g,"\\u003c")`, which both handles quotes/apostrophes safely (JSON string escaping) and prevents a business name containing `</script>` from prematurely closing the embedded script tag. Verified by generating cards for `Joe's Coffee & Tea` and `<script>alert(1)</script>` and syntax-checking + inspecting the output — both rendered safely with no injection and no syntax errors.
- **Grid rendering for all N in 4–12** via `clampN()`, including out-of-range and non-numeric inputs (values outside 4–12 clamp correctly; `NaN` falls back to 9).
- **Redemption reset preserves lifetime count**: both the main demo and the exported card set `stamps = []` on redeem while incrementing `lifetimeRewards`, and the lifetime counter is displayed both mid-cycle and on the reward screen.
- **Demo/setup storage isolation**: `pcl_setup_v1` and `pcl_demo_v1` are fully separate keys; resetting the demo never touches setup data and vice versa.
- **Exported card storage key is business-name-derived** (`pcl_card_` + slugified `bizName`), satisfying the "don't collide" requirement for the realistic case (different shops' cards are hosted on different origins, and browser localStorage is already origin-scoped, so this is defense-in-depth on top of that). Noted as a documented edge case below rather than "fixed," since it isn't a code defect.
- **Form validation**: export is blocked with a toast + focus if business name is empty or the staff PIN isn't exactly 4 digits; the PIN field's input handler strips non-digits and truncates to 4 characters as you type, so `setup.pin.length !== 4` is a reliable proxy for "exactly 4 digits."
- **No dead buttons**: every `id` referenced by `addEventListener` or `getElementById` in the markup has a corresponding handler; cross-checked the full `id="..."` list against wiring code.
- **file:// compatibility**: no ES modules, no `fetch()`, no `import`/`require` anywhere in the app. Only external reference is the specified qrcodejs CDN `<script src>` tag, exactly matching the required URL.
- **QR offline fallback**: all three QR call sites (single QR preview, 9-up counter sheet loop, page-load restore) guard with `typeof QRCode === "function"` and fall back to visible URL text without crashing.
- **Print CSS scoping**: `@media print` hides `body *` and re-reveals only `#print-sheet-area` and its descendants, positioning that element absolutely — a standard, correctly scoped "print only this element" pattern that won't leak other UI onto the printed page.
- **README factual accuracy**: every claim checked against the code (offline capability of the exported card, `file://` zero-dependency operation, QR CDN fallback behavior, localStorage persistence) is accurate. The honest single-device/no-sync positioning is prominent and not buried — "What it actually is (the honest pitch)" and the "Limitations" section both state plainly that stamps live in one phone's browser storage with no account/server/cross-device sync. No changes were needed to the README.

## Remaining limitations (documented, not defects)

- **Exported card's storage key collision is theoretically possible** if two different cards with business names that slugify to the same string are ever loaded from the *same browser origin* (e.g., a seller testing multiple `file://` exports in a browser that shares a null/file origin, or two clients' `card.html` hosted under paths on the exact same domain with identical shop names). In the realistic distribution model described in the README (each shop hosts its own `card.html` on its own domain/Netlify site), this cannot happen because localStorage is browser-origin-scoped. Not fixed because it's an inherent property of any single-file, no-backend localStorage design, and the realistic deployment path already avoids it — noted here for the record rather than papered over.
- **Staff PIN is a light deterrent, not real security** (plaintext in the exported HTML's source, shared 4-digit code) — already stated plainly in the README and is a correct, intentional trade-off for this product category.
- **No owner-side reporting/analytics** and **no cross-device sync** — both by design, both already disclosed prominently in the README.

## Revenue-Readiness score: 8/10

This is close to a clean, honestly-positioned, single-file product a solo operator could sell into local shops this week; the one real bug found (a plausible localStorage-corruption crash path in the exact file customers keep on their phones) has been fixed and regression-tested, and the README already does the hard, unusual work of stating the single-device limitation as a selling point rather than hiding it. It loses points only because the product's core value (multi-visit stamp tracking) still depends entirely on one customer never clearing a browser, switching phones, or losing that tab — a real objection every buyer will eventually raise, so close rate will hinge on how well the seller pre-empts it in the pitch rather than on anything fixable in the code.
